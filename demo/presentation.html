El problema

Houston es genial… para un solo equipo

Hoy (Houston referencia)

  • Single-tenant, local-first
  • 15 crates de engine sin org_id / tenant
  • Módulos teams/ y cloud/ son stubs
  • No hay identidad, ni roles, ni aislamiento

Para vender B2B se necesita

  • Múltiples organizaciones, grupos y usuarios
  • Roles y permisos (owner / manager / member)
  • Aislamiento real entre tenants — no negociable
  • Que los agentes corran con el contexto de cada cliente

No forkeamos Houston. Construimos un control plane multi-tenant por encima.

La decisión clave

El aislamiento se garantiza en los datos, no en el código

Un if en la aplicación se olvida, se rompe, se bypassa. Una política RLS de Postgres es la base de datos diciendo "no" — para toda query, siempre.

Defensa en profundidad

Aunque un handler tenga un bug de autorización, la RLS de Postgres y Storage es la última línea: ningún dato de otro tenant sale.

Probado, no prometido

Un leak-test automático actúa como gate de merge: si una sola fila u objeto de otro tenant se filtra, el build falla.

Arquitectura

Tres piezas, una invariante

Cliente
curl / UI / Postman · JWT en cada request
→
Orquestador Go
Auth (ES256/JWKS) → deriva (org, grupo, rol) → RBAC 403 → handlers /v1/*
→
Supabase
Postgres RLS · Storage RLS · Auth (Google SSO)
+
Claude Code
subprocess local por run · workspace aislado · API key inyectada

El orquestador nunca usa el service_role en paths de usuario: habla con Supabase con el JWT del usuario, así la RLS está siempre en efecto. El control plane es nuestro; el engine de Houston se reusa por debajo.

Modelo multi-tenant

Organización → Grupos → Miembros

org:owner

Dueño de la organización. Ve todos los grupos de su org, gestiona credenciales y miembros.

group:manager

Gestiona su grupo: crea agentes, administra a sus miembros.

group:member

Usa y corre los agentes de su grupo (y del grupo general del org).

Una función current_tenant() (security-definer) deriva (org_id, group_id, role) desde la membership del usuario autenticado — la misma fuente de verdad para la RLS y para el RBAC del middleware. Imposible falsificar el tenant desde el cliente.

Aislamiento en acción

Cero fuga, garantizado por RLS

Postgres (6 tablas tenant-scoped)

Cada tabla con FORCE ROW LEVEL SECURITY. Un usuario solo lee/escribe filas de su org y sus grupos visibles. El org:owner ve todos los grupos de su org; los runs son privados.

Storage (bucket houston)

Los objetos viven en {org}/{grupo}/agents/{id}/. Una policy RLS por prefijo espeja exactamente la lógica de las tablas. Los archivos de un tenant son invisibles para otro.

leak-test Actúa como Usuario A y afirma: 0 filas y 0 objetos de otra org/grupo. Gate automático del MVP.

El rol se enforce en el middleware Go (RequireRole); el acceso cross-grupo lo enforce la RLS. Un rbac-test automático verifica toda la matriz como comportamiento HTTP observable.

El agente

Crear → Correr

1 · Crear POST /v1/agents

4 fuentes: blank, template, ai-assist (Claude genera el CLAUDE.md), github. Nace scoped a org+grupo: fila en agents + CLAUDE.md en Storage.

2 · Correr POST /v1/agents/{id}/runs

Verifica acceso (RLS) → workspace aislado /tmp/houston-run-{uuid}/ → baja el contexto desde Storage → lanza Claude Code real con la API key inyectada → captura la salida → persiste el run. Concurrente.

"Crear un agente y correrlo" es el demo central del MVP — y funciona end-to-end, con una sesión real de Claude leyendo el contexto del tenant.

Cómo lo construimos

Rigor de ingeniería

Spec-as-source + TDD

Cada cambio de código exige una spec; los tests se escriben antes de implementar. 3 niveles: unit / integration / acceptance.

Correrlo de verdad caza bugs

El e2e contra Supabase real destapó 4 bugs que los tests mockeados no veían (policy de Storage, lectura de templates, validación de tokens asimétricos, recursión de RLS) — todos arreglados y deployados.

La invariante de aislamiento no es un comentario: es un test que rompe el build si se viola.
